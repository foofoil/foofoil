# 浮箔（foofoil）：Agent 桌面呈现能力方案

> 产品与技术方案修订稿 · 2026-10-16。
> 基于当前工作区源码静态核对修订；未进行 IPC 原型、Release 签名环境或窗口交互验证。下文 CLI、协议及自动化能力均为设计提案，不代表已经实现。

前置任务：[历史记录与文件处理](history-file-handling-implementation-plan.md)。

Agent 实施入口：[分步实施计划与 Checklist](foofoil-agent-desktop-terminal-implementation-plan.md)。后续实施 Agent 按该文档记录进度、验证证据与交接信息；本文作为产品行为依据。

## 1. 定位与目标

foofoil 的主要定位仍是**轻量级 macOS 桌面悬浮参考板**。Agent 接入是现有展示能力的一种新增入口：人类通过 GUI 打开参考内容，Agent 通过受控接口创建和更新展示窗口。

foofoil 不负责模型推理、任务编排或 Agent 执行环境。它打开调用方提供的文件，将结果呈现在桌面，并让用户保有移动、缩放、隐藏、置顶及关闭窗口的控制权。浮箔负责查看文件，不承担原文件的保管与归档。

核心增益是：内容脱离聊天记录与终端后仍可见；Agent 可持续更新同一窗口；更新保留用户布局，并提供机器可解析的结果。

命名约定：应用名称 `foofoil`；拟议 CLI 命令 `foil`；Skill 名称 `foofoil`。发布前检查命令名称冲突。MCP Adapter 后续按需提供。

## 2. 项目现状与复用边界

| 能力 | 当前实现 | 本方案的处理方式 |
| --- | --- | --- |
| 多窗口与窗口集合 | `AppDelegate.windowControllers`、`FloatingWindowController` | 复用窗口生命周期，增加自动化窗口索引 |
| 悬浮、拖动、缩放、透明度和边框 | 现有 AppKit 窗口与控制器 | 复用；自动化更新增加保留用户属性的策略 |
| 图片、SVG、Markdown、PDF、网页 | 已有内容打开和渲染路径 | 复用渲染器，按阶段开放自动化输入 |
| 内容状态与持久化 | `AppState`、`WindowConfig`、`SettingsStore` | 复用；区分窗口身份、内容身份与自动化归属 |
| 历史、缓存和索引 | 已有历史存储及应用托管缓存 | 统一为原文件引用，复用普通／无痕模式，增加失效历史自动清理 |
| 本地打开入口 | 文件关联、Finder 服务、分享扩展、自定义 URL | 参考现有导入流程；不等同于有确认响应的自动化协议 |
| IPC | 存在面向内部内容模块的 XPC 连接 | 不能直接视为外部 CLI 控制服务；单独验证边界与可用性 |

## 3. 目标场景与首版范围

首版围绕持续参考，优先支持以下场景：

1. Agent 生成 SVG 架构图，创建参考窗口，随后替换为新版图。
2. 在同一 Markdown 窗口中更新报告或任务进度，保留用户调整的位置和尺寸。
3. 两个窗口展示前后对比，用户可独立移动、隐藏和关闭。

首版输入仅包括 Markdown、普通文本、图片和 SVG 文件。Agent 入口仅作为只读呈现终端，不开放可编辑便笺、文本编辑、直接输入内容创建便笺或写回原文件的能力；文本和 Markdown 通过原文件只读展示，刷新由调用方修改原文件后显式请求。GUI 原有便笺能力独立保留。PDF 指定页随后提供；远程网页、本地 HTML、媒体、目录、压缩包及其他复杂输入不进入首版自动化范围。GUI 原有内容能力继续保留。

简短回答、日志流和单纯进度百分比保留在 Agent 原界面。文件变化监听、布局模板、窗口组、MCP 和远程桥接均后置，首版不预建相关基础设施。首版要求显式调用 `update`。

## 4. 架构与实现原则

```text
本机 Agent / 人类脚本
          │
    foofoil Skill（操作说明）
          │
       foil CLI
          │
   本机请求响应与授权
          │
   应用内自动化入口
   ├── 协议校验、归属与请求状态
   ├── board_id → 现有窗口控制器索引
   └── 内容准备与提交策略
          │
   AppDelegate / AppState / FloatingWindowController
          │
       现有渲染视图
```

自动化入口是现有应用能力前的薄层，不新建第二套窗口、渲染或历史系统。图中职责不要求各自建设独立框架；按实际复杂度拆分类型。

保持项目原生、轻量和渐进实现的原则。优先使用系统能力，不为 CLI 引入独立语言运行时、常驻守护进程或大型服务框架。内部内容模块继续作为开发与交付机制，不扩张为用户可见的插件平台。

Skill 负责说明如何使用 CLI，不承担通信或授权。CLI 必须在没有 Skill 的情况下也可独立使用。MCP 将来复用同一控制契约。

## 5. 阶段 0：先验证沙盒与内容交付

Release 应用启用了 App Sandbox。CLI 能读取某个文件，不代表应用收到其绝对路径后也能读取；路径校验与文件访问授权是两个问题。

在确定 IPC 传输方案前，完成以下原型验证：

- 应用未运行时，CLI 能启动应用、等待控制入口就绪，并获得确定响应。
- CLI 将原文件引用及所需访问能力交付到沙盒应用，应用能够直接读取原文件，无需持久复制文件正文。
- 在目标签名方式和 Release 配置下验证通信及文件交付，不只测试 Debug。当前 Debug 具有用于测试的额外网络监听权限。
- Agent 保留源文件时能够持续读取；源文件删除后，重新加载明确失败，不使用旧缓存替代原文件。普通箔重启恢复时重新解析文件引用和访问授权。
- 启动请求不触发无关空白窗口、意外批量恢复或抢夺用户输入焦点；具体行为与既有启动偏好协调。

交付方案以原文件引用和经验证可用的文件访问能力为基础；不以传输正文并持久保存副本作为默认方案。具体方案在原型后确定，记录签名、权限、文件大小及关联资源限制。不因实现方便默认关闭沙盒、扩大目录权限或增加监听权限。

本地文件统一直接引用原文件，不增加快照／引用双模式。源文件变化后，首版通过显式 `update` 重新读取，不自动监听。Agent 首版 Markdown 限定为自包含的文字、表格和代码块；需要图片时由调用方创建独立图片或 SVG 文件另开箔片。不加载 Markdown 的相对图片或远程图片，不为此自动申请整个目录权限；检测到不支持的资源引用时，CLI 返回成功结果中的结构化警告，展示中保留可识别的资源不可用提示。GUI 已有 Markdown 资源能力不因该限制而删除。

CLI 的安装、应用发现、版本匹配和升级方式也在阶段 0 确定。不得依赖开发者工作区路径或要求用户手工修改应用包。

## 6. 窗口身份与归属

- `board_id` 是自动化展示窗口的稳定标识，在窗口内容更新时保持不变。
- 现有内容 ID 继续服务历史、缓存和异步逻辑，不将其直接改造成窗口身份。
- 每个自动化窗口记录创建归属、当前内容修订号和普通／无痕属性。用户手动创建的窗口不自动加入 Agent 可管理范围。
- 首版会话凭证默认只允许创建、查询、更新及关闭自身获授权窗口。
- `list` 默认只返回授权范围内的窗口，不返回其他调用方或人工窗口的标题、路径及内容信息。
- 任意同用户进程的强隔离不作为默认承诺。凭证机制必须说明保护范围；调用方自报名称仅用于标注，不能作为权限依据。
- 凭证不得进入内容、普通日志或可分享的示例输出；提供撤销方式。凭证传递及存储方式在阶段 0 确定。

人工替换自动化窗口的内容时，立即解除原调用方的控制权，避免后续更新覆盖用户打开的新资料；移动、缩放、隐藏、置顶等窗口操作不解除控制。原调用方后续写请求返回明确的权限错误。

普通箔跨应用重启恢复后作为人工窗口，原 `board_id` 与该次运行的控制凭证失效；从历史重新打开也不恢复 Agent 控制权。首版不提供窗口认领、凭证恢复或自动重连，调用方再次需要展示时显式创建新箔。

来源信息放在现有信息面板或右键菜单，标注由哪个调用方创建；该名称只用于展示，不作为授权依据。不增加常驻来源标签、工具栏或窗口组管理。

## 7. MVP CLI 与响应契约

```bash
# 创建普通箔，引用原文件并进入历史，返回 board_id
foil show ./architecture.svg --title "系统架构" --json

# 临时展示使用现有无痕箔，不进入历史，退出后不恢复
foil show ./temporary-report.md --incognito --json

# 更新内容，默认保留用户的窗口属性
foil update <board-id> ./architecture-v2.svg --json

# 查询当前凭证可访问的窗口
foil list --json

# 关闭获授权窗口
foil close <board-id> --json
```

CLI 将相对路径解析为绝对路径，交付原文件引用及必要的访问能力；绝对路径本身不表示已经获得沙盒访问权。普通／无痕属性在创建时指定，`update` 不改变该属性。`show` 始终新建，不按同名文件查找或接管现有空白箔；`update` 仅操作指定 `board_id`。首版不提供原始文本直传、创建可编辑便笺或文件写入命令。

协议至少定义以下字段或等价语义：

| 项目 | 要求 |
| --- | --- |
| `protocol_version` | 明确版本和不兼容错误 |
| `request_id` | 在明确的凭证作用域和保留期限内去重；相同 ID、不同请求体应拒绝 |
| `board_id` | 定位稳定窗口；创建成功后返回 |
| 内容输入 | 明确原文件引用、类型、大小及访问能力，不依赖文件后缀猜测全部语义 |
| `revision` | 成功提交内容后的修订号 |
| `expected_revision` | 可选的条件更新；过期请求返回冲突，不覆盖较新内容 |
| 请求状态 | 区分已接受、已就绪和失败；四命令 MVP 默认等待确定结果 |
| 错误 | 稳定错误码与可读说明；stdout 输出结构化结果，诊断走 stderr |
| 超时 | 明确启动、内容准备与响应超时；超时不等同于请求未执行 |

成功响应示例：

```json
{
  "protocol_version": 1,
  "request_id": "req-001",
  "status": "ready",
  "board_id": "opaque-board-id",
  "revision": 1
}
```

`ready` 表示内容已完成该类型所需的读取和验证，并提交给目标窗口，不承诺屏幕像素已经完成绘制。阶段 0 和实现规格应进一步列出各类型的就绪条件。

建议错误码包括 `BOARD_NOT_FOUND`、`PERMISSION_DENIED`、`CONTENT_UNREADABLE`、`UNSUPPORTED_CONTENT`、`CONTENT_INVALID`、`REVISION_CONFLICT`、`CONTROL_PAUSED`、`PROTOCOL_MISMATCH` 和 `TIMEOUT`。对未授权目标采用一致响应，避免泄露其是否存在。

失败返回非零退出码。重试必须沿用原 `request_id`，在去重有效期内不得重复创建窗口或重复提交更新；超出期限后的处理规则需明确说明。

## 8. 内容更新契约

更新采用“准备 → 再校验 → 提交”的过程：

1. 校验权限、输入类型和大小，取得原文件访问权限，读取并验证待展示内容；允许必要的内存准备和短期渲染资源，不生成持久正文副本。
2. 准备完成后重新检查窗口仍存在、归属未改变、控制未暂停，以及修订条件仍满足。
3. 在主线程提交内容，增加修订号并返回结果。昂贵 I/O 和解析不占用主线程。

准备失败时不主动清空原有展示状态及窗口属性，释放本次未提交资源。浮箔不为失败回退保存旧版本文件；原文件已被覆盖或删除时，不保证旧内容仍可重新读取。用户关闭窗口后，任何在途请求均不得创建替代窗口或重新弹出。

同一窗口的写操作按应用接受的顺序处理。不能仅依赖主线程串行，因为内容准备可能异步完成。请求重试与关闭也必须纳入顺序规则。首版优先使用有界队列和明确限流，不引入无界任务；后续若合并中间更新，应向调用方明确报告被替代状态。

默认保留以下用户属性：位置、尺寸、置顶、透明度、边框和隐藏状态。内容更新不得重新触发普通打开流程中的自动窗口布局或恢复默认样式。同类内容更新保留缩放与滚动位置，位置超出有效范围时截断到可用位置；更换内容类型时保留窗口布局，内容缩放和阅读位置恢复该类型默认值。

同路径文件被覆盖后，显式 `update` 必须刷新内容。不能只用 URL 是否变化判断是否重新加载；应使用内容修订号触发重新读取与渲染，不以创建持久快照规避刷新问题。

首版自动化更新不直接承诺复用全部 GUI `open*` 方法即可满足这些约束，应检查其身份轮换、清理、保存和布局副作用。

## 9. 焦点与用户控制

- 创建窗口不激活应用、不成为键盘输入目标；初始置顶、透明度等沿用浮箔现有新箔默认设置，不另设 Agent 专属置顶偏好。首版不开放调用方反复修改窗口层级的接口；更新保留用户当前设置。
- 更新不得改变键盘焦点，不改变用户隐藏状态，不唤醒或重新展示用户已关闭的窗口。
- 用户仍可移动、缩放、隐藏、关闭或接管内容。
- 提供暂停自动化写入的入口。暂停后拒绝新的创建、更新和关闭请求，并阻止在途写入提交；保留用户操作和授权范围内的只读查询。
- 限制窗口数量、创建频率、请求大小和排队数量；达到限制时返回明确错误。

无焦点行为需实际验证首次启动、已运行、应用隐藏、多显示器、全屏 Space 和用户正在其他应用输入等情形。

## 10. 独立前置任务：历史记录与文件处理

完整产品规则、分步 Checklist 和验收见 [历史记录与文件处理实施计划](history-file-handling-implementation-plan.md)。该任务独立实施，H01—H06 验收完成后再开始 Agent 接入；此处仅保留边界摘要，避免重复维护。

- 本地已有文件直接引用原文件，历史记录定位、访问授权与展示状态；不按文件类型隐式复制正文。
- 剪贴板文件引用仍引用原文件，网址仍打开网址；剪贴板文本／Markdown／HTML 和图片数据自动保存为应用托管内容，标记“来自剪贴板”，普通历史可直接恢复，无需另存为。
- 剪贴板同时含图片与网址时优先图片数据，网址只作可选来源；仅有图片地址时按网址处理。
- 删除历史时释放对应托管正文及派生缓存；活动窗口或其他引用仍使用时延后实际删除。不能删除用户原文件，也不能让已删除历史被窗口或索引任务复活。
- 无痕剪贴板不写历史、不恢复，最后使用者释放后清理临时资源。原文件形式的 Agent 临时展示仍由调用方保管文件。
- 自动清理找不到文件的历史默认开启、可以关闭；书签能追踪则保留，权限或离线问题不误判。托管剪贴板内容按其正文是否可用判断，不因缺少外部来源而清理。
- GUI 截图、便笺与分享工作流不新增强制另存为要求；Agent 接口依然不开放剪贴板、便笺、编辑或文件写入。
- 普通 Agent 更新复用原历史项，不逐次建立版本快照；Agent 退出不自动关闭窗口，源文件删除后不保证可重新读取。

旧记录处置、托管正文与可淘汰派生缓存的区分、活动引用保护和相关测试均在前置文档管理；本次文档拆分不执行数据删除或应用代码修改。

## 11. 后续内容能力

### PDF

复用 PDFKit，增加无需弹框的指定页控制。`--page` 使用从 1 开始的页码；文档损坏、加密限制及显式指定的页码越界返回明确错误。更新同一 PDF 时默认保留当前页；当前页超出新版页数时落在新版最后一页，显式指定页码优先。

现有 PDF 视图在 URL 改变时重建文档，因此还需解决同路径更新及加载完成后应用目标页码的问题。

### 网页与 HTML

网页能力开放前，单独定义存储、脚本、远程资源、导航、下载、弹窗及外部协议策略。当前普通网页视图不能直接视为 Agent 专用隔离环境。

静态报告与任意网站导航应有不同策略。先验证本地静态报告的必要性，再决定是否支持完整网页能力。不得自动继承用户登录状态或扩大本地文件读取范围。

## 12. Skill 设计

```text
foofoil/
└── SKILL.md
```

Skill 应说明：

- 适用场景：图表、参考资料、长报告和持续状态；避免为简短回复创建窗口。
- 检测 CLI、应用及协议版本是否可用。
- 将产物写入文件；临时展示使用无痕箔，需要历史的产物保存在稳定位置后使用普通箔。
- 保留展示期间需要读取的原文件，不能将成功响应理解为浮箔已经保存副本。
- 生成受支持的自包含文件，调用命令并解析结构化结果和警告；Markdown 中需要图像时，另开图片／SVG 箔，不自动扩大目录读取范围。
- 仅使用只读呈现接口，不尝试创建、接管或编辑 GUI 便笺。
- 同一报告持续更新时复用窗口，不同资料或前后对比显式新建窗口。
- 记录 `board_id` 和修订号，优先更新已有窗口。
- 用户关闭窗口或暂停控制后尊重该状态，不自动改用 `show` 重新弹出。
- 超时后使用相同请求 ID 重试，遵循去重期限与错误处理规则。
- 展示失败时回退到 Agent 原界面。
- 不同 Agent 的安装与执行权限说明分别维护，不承诺统一安装机制。

凭证和窗口归属由应用协议保证，不能依靠 Skill 中的文字约定。

## 13. 实施路线

**前置任务：历史记录与文件处理。** 按[独立实施文档](history-file-handling-implementation-plan.md)完成 H01—H06，覆盖本地原文件引用、剪贴板自动缓存与来源标记、随历史释放缓存、默认失效历史清理及回归验收。进度仅在该文档维护。

**阶段 0B：约束验证与接口定稿。** 验证 Release 沙盒原文件访问、通信、后台启动和确定响应；确定 CLI 分发、凭证机制、稳定身份与各类型就绪条件。输出小型原型验证记录。

**阶段 1：四命令只读闭环。** 支持自包含 Markdown、只读文本、图片和 SVG 文件，不开放可编辑便笺。稳定窗口身份、归属控制、保留布局、无焦点更新、失败保留旧内容、幂等重试、暂停控制及有界请求处理均属于 MVP 必需项，不延后到可靠性阶段。支持创建无痕箔，普通箔沿用统一历史行为。提供首版 Skill。

**阶段 2：阅读与持续使用。** 支持 PDF 指定页；验证普通箔引用原文件的恢复及书签刷新，根据实测优化更新合并、派生缓存和索引成本。不新增 Agent 专用历史体系。

**阶段 3：按需扩展。** 有实际需求后再启动网页与 HTML、MCP、窗口分组、布局模板和远程桥接的独立评估；首版不预建基础设施。不建设完整 Agent Dashboard。

## 14. 验收标准

| 场景 | 预期结果 |
| --- | --- |
| 应用未启动时执行 `show` | 获得确定结果，不出现无关空窗，不抢夺输入 |
| 应用已运行时执行 `show` | 返回本次运行内稳定的 `board_id`，新建一个目标窗口，不接管空白箔或同名资料 |
| 同一请求超时后重试 | 在去重有效期内不重复创建或提交 |
| 更新同一窗口 | `board_id` 不变，修订号增加，用户窗口属性保留 |
| 用户正在其他应用输入 | 创建与更新均不打断输入 |
| 同路径文件内容改变后更新 | 展示新内容，不因 URL 相同而跳过加载 |
| 文件损坏、不可读或类型不支持 | 非零退出码及明确错误，不主动清空原展示；不保证已被外部删除／覆盖的旧内容可重读 |
| 准备期间用户关闭窗口 | 返回窗口不存在，不重新创建窗口 |
| 用户替换窗口内容 | 原调用方立即失去控制权，不能继续覆盖用户资料 |
| 用户移动或缩放窗口 | 保留原调用方控制权，后续更新不覆盖布局 |
| Agent 展示文本与 Markdown | 只读展示，不提供便笺创建、编辑或写回文件能力 |
| Markdown 含相对或远程图片 | 不自动读取或下载，响应带警告并提示资源不可用 |
| 普通箔重启恢复或从历史重新打开 | 作为人工窗口，旧 board_id 和控制凭证不可继续使用 |
| 并发和过期修订更新 | 按约定顺序处理，冲突明确，不由完成时间偶然决定 |
| 其他调用方查询或操作 | 不暴露未授权内容，不能修改目标窗口 |
| 暂停自动化控制 | 新写入被拒绝，在途写入不提交，GUI 仍可用 |
| Agent 退出但源文件仍在 | 窗口继续存在，不因调用方退出而关闭 |
| 源文件删除后重新加载或历史恢复 | 不从正文缓存回退；明确失败，历史按清理设置处理 |
| 图片、文本、视频等本地文件打开 | 均引用原文件，不因类型不同持久复制正文 |
| 文件移动或改名后书签仍能定位 | 保留历史，刷新引用并打开原文件 |
| 确认文件丢失且清理设置开启（默认） | 删除历史项、相关索引及失效待恢复配置，清理无引用派生缓存 |
| 清理设置关闭 | 保留失效项，打开时提示原文件不可用 |
| 权限失效、磁盘离线或暂时读取失败 | 不误判为已删除，不自动移除历史 |
| Agent 以无痕模式临时展示 | 不写历史、不参与重启恢复，仍直接读取原文件 |
| 清理历史时目标窗口仍打开 | 不强制关闭窗口，不删除用户文件 |
| GUI 剪贴板文本与图片 | 普通箔自动缓存并标记来源，可直接从历史恢复，无需另存为 |
| 删除剪贴板历史 | 删除记录及索引，托管正文在最后使用者释放后删除；不复活历史 |
| 连续多次更新 | 历史数量、缓存和队列增长符合既定策略 |
| Release 签名构建 | 通信与文件读取成功，不依赖 Debug 额外权限 |
| 人工使用回归 | 原有打开、拖放、恢复、历史及多窗口体验不退化 |

验证包括协议与更新状态的聚焦测试，以及真实 macOS 窗口交互检查。实现阶段按照项目要求构建、运行相关测试并启动应用验证；本方案修订本身不代表上述验收已经通过。

## 15. 已确定的产品决策与验证边界

以下产品决策作为实现依据，不再作为开发前置的待定问题：

| 问题 | 决策 |
| --- | --- |
| 核心场景 | 持续参考：架构图、前后对比、文档和报告；简短回复、日志流及单纯进度百分比留在 Agent 原界面 |
| Agent 能力边界 | 只读文件呈现，不开放可编辑便笺、原始文本直传创建便笺或文件写入 |
| 新建还是复用 | `show` 新建，`update` 按 ID 更新；不自动接管空白箔或同名内容 |
| 来源提示 | 放在现有信息面板或右键菜单，不增加常驻标签或工具栏 |
| 置顶与焦点 | 创建沿用新箔默认设置且不抢焦点，更新保留用户设置与隐藏状态 |
| 重启后控制 | 普通箔恢复为人工窗口，原控制凭证和 board_id 失效；无痕箔不恢复 |
| Markdown 资源 | Agent 首版仅自包含文字、表格和代码块；图像独立展示，不自动请求目录权限或下载资源 |
| GUI 剪贴板正文 | 自动缓存并标记来源，历史删除后释放缓存，不要求另存为；不扩展 Agent 编辑能力 |
| 原文件丢失 | 默认自动清理历史，可关闭；权限或离线问题不等同于删除 |
| 文件监听与生态扩展 | 首版显式更新，不做监听，不预建 MCP、远程桥接或分组体系 |

使用频率和用户是否习惯持续参考可在首版交付后收集反馈，不作为继续扩张功能的前提。

仍需通过原型验证的工程约束：Release 沙盒下原文件访问能力如何传递与恢复，以及后台启动、创建和更新能否可靠地不抢焦点。这些必须实际通过后才能确定传输实现，不以文档声明代替验证。CLI 安装与应用发现、协议超时、去重期限、队列限额和各类型就绪条件在阶段 0B 的实现规格中定稿，不再列作产品待定问题。

**核心原则：复用 foofoil 已有的桌面呈现能力，通过明确、受控、可验证的只读自动化契约，让 Agent 持续呈现工作上下文，同时保留用户对桌面的控制。**
