# foofoil 终端箔与统一控制接口设计

> 状态：开发实现与本机验收完成，待发行验收（主应用取消沙盒，仅站外分发）｜2026-10-21  
> 范围：终端箔（Terminal Foil）、`foil` CLI、应用控制接口及 Agent 集成

## 1. 背景与定位

foofoil 是轻量级 macOS 悬浮参考应用，基于 SwiftUI、AppKit，支持独立悬浮窗口、历史记录与恢复。现有架构以轻量 Core 和内部能力模块为原则；能力随产品交付，不向用户暴露独立扩展安装、启用或更新概念；终端箔已决定作为 **Core 内置内容类型**。

新增「终端箔」：在悬浮窗口中提供真实的交互式终端，允许配置工作目录、环境变量和初始化命令；从历史记录再次打开时重建相同的启动环境。进一步让终端箔成为 foofoil 的高级控制入口。

**核心原则：终端箔是控制接口的客户端，不是控制中心的实现。** 外部 Terminal、Agent 和 GUI 都应复用相同的应用控制能力。

### 当前仓库基线与本次变更

当前仓库已有 `AgentCLI/Foil.swift`、`foofoil/AgentTerminal/` 和协议 v1，不能按控制接口尚不存在来实施。现有 `foil show FILE` 新建展示窗口，`update BOARD FILE` 更新内容，`list/close` 仅操作当前凭证拥有的窗口；已有运行 ID、凭证、暂停/撤销、revision、请求去重与有界队列。传输通过标准打开文档事件交付文件和请求信封，详见 [现有协议及原型记录](agent-terminal-protocol-v1.zh-CN.md)。其中 Agent terminal 指 Agent 展示控制能力，不是本设计的交互式 PTY 终端。

本设计增加交互式终端和通用窗口控制。复用已有 CLI、控制状态与窗口管理，先明确协议演进及迁移边界，不并行建立第二套控制系统。前置沙盒原型已记录阻塞。用户随后确认取消主应用沙盒、仅站外分发、不迁移旧容器数据；正式实现直接在主应用承载终端，保留 Hardened Runtime、签名、公证及 macOS 隐私控制。

## 2. 目标与非目标

### 目标

1. 在箔片中运行真实交互式 Shell，兼容 SSH、Vim、TUI 程序。
2. 显式保存启动配置，从历史记录重新打开时可重复执行。
3. 支持 `foil` CLI 控制正在运行的 foofoil：列出、打开、显示、隐藏、关闭箔片。
4. 提供稳定的结构化结果，供脚本和 Agent 使用。
5. 保持窗口管理、历史持久化、扩展边界与现有 foofoil 架构一致。

### 非目标（首版）

- 替代 Ghostty/iTerm2 的完整终端功能集。
- 关闭后恢复进程内存、Shell 状态或未保存的 TUI 编辑状态。
- 多标签、分屏、内置 SSH 密钥管理。
- 无授权地让 Agent 接管用户现有终端。
- 在 Core 中引入独立的后台常驻服务或第二套历史数据库。

## 3. 用户场景

| 场景 | 保存的启动配置 | 重新打开后的行为 |
| --- | --- | --- |
| 本地开发 | 工作目录 `~/github/foofoil` | 打开交互式 Shell，进入目录 |
| 远程维护 | `ssh server` | 新建 SSH 连接 |
| Agent 开发 | `opencode` | 启动新的 OpenCode 客户端进程 |
| 日志观察 | `ssh server 'tail -f /var/log/app.log'` | 新建实时日志流 |
| 控制中心 | 普通 Shell，预置 `foil` 可执行路径 | 使用 `foil list` 等命令管理箔片 |

**重新打开 ≠ 会话恢复。** 首版只重建配置；后续可通过 tmux 等机制实现重新附着，但应单独设计。

## 4. 总体架构

```text
GUI ──────────────┐
foil CLI ── IPC ──┼──> Application Control Service ──> AppState / 窗口控制器 / 历史仓库
Agent ──── CLI ──┘                  │
                                   └──> 箔片运行时
                                           ├── Image / PDF / Web / Markdown
                                           └── Terminal Foil
                                                  └── PTY ── Shell / SSH / TUI
```

- **Application Control Service**：复用现有 `AppState` 和窗口控制器，不创建平行的窗口生命周期管理器。GUI 可直接调用内部服务；IPC 是其外部适配层。
- **CLI**：独立轻量可执行文件，解析参数、通过 IPC 发送请求、格式化输出，不承载业务规则。
- **Terminal Foil**：一个箔片内容类型，持有终端视图和运行时会话；可调用与外部终端相同的 `foil` CLI。
- **Agent**：首选调用 CLI 和解析 JSON；不要求终端箔处于打开状态。

控制服务是逻辑边界，首版不需要构建通用命令总线或插件框架。

## 5. 终端箔设计

### 5.1 启动配置

建议字段：

```swift
struct TerminalLaunchConfiguration: Codable {
    var shellPath: String?           // nil 表示用户默认 Shell（首版 zsh/bash）
    var workingDirectory: String?
    var environment: [String: String]
    var startupCommands: String      // 多行 Shell 代码，明确标记为可信脚本
}
```

- 工作目录通过启动进程配置设置；环境变量通过进程环境传入。
- 初始化命令必须在**同一个交互式 Shell** 内执行，才能保留 `cd`、`export` 等状态；不能逐条启动独立 `Process`。
- 具体实现可在 Shell 已启动并就绪后向 PTY 输入 `source` 命令；应处理引号转义、Shell 启动脚本、命令回显、初始化竞争条件和临时脚本清理。不要假定 `zsh -c` 结束后仍保留交互式会话。
- 新建和历史主动重开直接启动并执行可选脚本，不提供启动方式选择。
- 不自动把终端历史转化为启动脚本；不在配置中保存明文口令、token 或私钥。
- `environment` 仅保存用户显式配置的非敏感覆盖项，不序列化进程继承环境。敏感值首版由用户在启动后输入或由外部工具获取；不得进入历史、日志或 `inspect` 输出。
- 首版明确支持交互式非登录 zsh/bash，分别实现并验证初始化方式；其他 Shell 和登录模式暂不开放，校验阶段直接拒绝不支持的 Shell。
- 初始化就绪不得依赖固定延时或匹配可定制提示符。原型须证明 Shell 专用启动钩子或握手机制可在用户启动脚本之后、用户输入之前执行一次初始化；定义启动脚本阻塞、初始化失败及取消的结果。

普通终端在独立历史字段保存最多 500 行、128 KiB 的只读纯文本输出，周期保存，关闭时补存；无痕终端不落盘。旧记录不重放给 PTY，不保存 TUI 备用屏幕。

#### 主动打开与自动恢复

- 用户创建终端或主动从历史重开已关闭的终端：载入配置并直接执行脚本，建立新会话；重新显示正在运行的窗口不重复执行。
- 应用启动恢复、崩溃后恢复：恢复窗口、配置和有上限的只读输出记录，显示“待启动”，用户点击启动后执行脚本；不得自动重复执行命令。
- 同一配置可以主动打开多个实例，每个实例独立执行，界面应明确这一行为。
- 首版不提供自动重启任务；未来如需支持，单独增加显式选项和重复执行规则。

### 5.2 终端引擎

候选：SwiftTerm（原生 Swift / AppKit / PTY）。在引入前验证：

1. 当前版本 API 与 SwiftUI `NSViewRepresentable` 桥接。
2. 中文输入法、Unicode、组合键、复制粘贴和焦点行为。
3. OpenCode、Vim、SSH、终端尺寸变化和 ANSI 输出。
4. Release 包体积、启动耗时、空闲/运行内存与许可证义务。

**选型决策**：优先集成 SwiftTerm，前提是核实所用版本的许可证及依赖许可证与 foofoil 当前 MIT 许可证兼容，并履行必要的声明义务。终端功能兼容性、Release 包体积和运行性能在开发完成后实测；不设未经测量的体积上限。终端箔直接内置 Core，不作为独立扩展。若验证不通过，再评估替代终端引擎。

### 5.3 生命周期

- **隐藏**：窗口不可见，PTY 和进程继续运行。
- **关闭**：若检测到正在运行的前台或后台任务，先弹出确认；取消则保持会话。无任务时直接关闭。确认后结束终端会话并保留启动配置/历史，先请求正常退出，超时后按明确策略处理受管理的进程组。不得承诺清理所有主动脱离管理关系的进程。
- **任务检测**：不能只判断 Shell 是否存活；结合 PTY 前台进程组及子进程状态识别活动任务。Shell 内建命令、脱离进程组的后台任务等可能无法准确识别；状态不确定时保守提示。应用退出及 CLI 关闭应定义一致的非交互处理策略，避免确认框永久阻塞自动化。
- **从历史重新打开**：启动新的 PTY 和 Shell，按配置执行初始化。
- **应用退出**：汇总活动/不确定会话，由 GUI 确认；取消则取消退出。确认后采用与关闭一致的清理策略，不可只销毁视图。
- **CLI 关闭**：遇到活动或不确定任务立即返回 `CONFIRMATION_REQUIRED`，不等待 GUI 对话框。调用方使用显式 `--force` 再次请求以授权终止；空闲会话可直接关闭。`--force` 只授权受管理会话的终止，不扩大进程清理范围。
- **受管理范围**：记录会话身份和进程组，关闭时先撤销输入并请求正常终止，宽限期后升级终止信号并回收直接子进程。信号顺序、宽限期及上限必须在原型后固化并测试；不得仅凭过期 PID 杀进程，也不得递归终止同用户的无关进程。对 disown/setsid 等脱离范围的进程，明确剩余风险。
- **Shell 已退出**：记录退出码和启动配置后直接关闭箔片，不再提供窗口内重启入口；需要新会话时从历史重开。

运行时状态（PTY、PID、退出码、会话 ID）不得直接当作持久化启动配置。终端运行时应避免在窗口重绘时被重复创建。

### 5.4 交互

终端获得焦点时，Ctrl+A/E/P/N 等按键优先交给终端程序；应用级快捷键须有明确的冲突处理。支持调整字体、背景不透明度，保持文字可读；窗口位置、大小、置顶与历史行为复用现有机制。所有界面字符串纳入 `Localizable.xcstrings` 的中英文资源。

## 6. `foil` CLI 设计

以下区分已有契约与拟新增能力。保留 `show FILE` 的现有含义，使用 `reveal ID` 显示已有窗口，避免命令冲突。以下为已接入的通用控制命令：

```sh
foil show ~/Documents/spec.md       # 已有：新建 Agent 展示窗口
foil update <board-id> ~/Documents/spec.md  # 已有：更新所属窗口
foil list --json                    # 已有：当前凭证所属窗口
foil close <board-id>               # 已有：关闭所属窗口
foil list --scope all --json        # 拟新增：通用窗口列表
foil open ~/Documents/spec.md       # 拟新增：通用内容打开
foil reveal <id>                    # 拟新增：显示已有窗口
foil hide <id>                      # 拟新增
foil close <id> --scope all          # 拟新增：通用关闭
foil close <id> --scope all --force  # 拟新增：授权终止活动终端
foil inspect <id> --json
foil set <id> opacity 0.85
```

第二阶段再考虑：

```sh
foil terminal create --title Dev --cwd ~/github/foofoil --command opencode
foil open --stdin --type markdown
foil workspace save development
foil workspace load development
```

设计约束：

- 统一窗口定位，但分别定义持久化配置 ID、当前运行窗口 ID 和终端会话 ID；已关闭或跨应用运行的窗口 ID 不得指向新窗口。现有 board_id/revision 语义保留，禁止把历史 ID 直接当运行实例 ID。
- 现有命令默认作用域和 JSON 默认输出保持不变；通用窗口访问通过显式 `--scope all` 或新命令进入，终端创建能力通过类型能力协商暴露。人类可读输出可使用显式选项，不静默改变现有 stdout 契约。
- 现有调用方归属继续服务 Agent 展示窗口；通用控制允许同用户显式访问人工窗口。应用内暂停必须阻止通用写操作，撤销继续作用于已注册凭证。宽松授权不应让新传输入口绕过暂停/撤销。
- 协议变更先列出兼容矩阵和迁移步骤；可扩展能力通过握手协商，若变更既有字段或语义则提升协议版本并明确拒绝不兼容客户端。
- 标准输出仅放结果；错误写标准错误，并使用明确退出码。
- 版本化 IPC 协议，输入做大小限制与类型校验。
- `--self` 等上下文命令可利用注入的 `FOOFOIL_TERMINAL_ID`，但环境变量仅是标识，**不是授权凭证**。
- CLI 应可在系统 Terminal 中独立工作；不能依赖终端箔。
- CLI 名称 `foil` 需在发布前检查现有命令冲突和分发方式。

## 7. IPC 与安全边界

**已确定：首版采用 Unix Domain Socket + JSON 协议**，由 foofoil 主进程提供本机控制端点；CLI 作为客户端。本次经用户明确确认取消主应用沙盒；Unix Socket 作为常规控制传输，保留文件事件用于冷启动、发现和旧客户端。控制服务与 IPC 传输层解耦，未来如需适配 XPC 或沙盒发行，再独立评估迁移。

**已确定：首版权限宽松，但限定为当前 macOS 用户。** 同一用户下的 CLI、脚本及 Agent 默认可调用已公开的箔片控制能力，不引入逐次授权或复杂权限角色；不允许其他本机用户直接连接控制端点。

最低安全约束：

1. Socket 放在仅当前用户可访问的目录，设置严格目录及 Socket 权限，并在可行时校验连接对端的本地用户身份；不能只依赖客户端传来的环境变量或声明身份。
2. 协议版本化，限制请求大小，校验参数类型、路径和操作目标；对并发与重复请求定义稳定行为。
3. 控制服务**不提供通用任意命令执行 `exec` API**。通过 `foil terminal create` 指定启动命令属于显式终端创建操作，终端创建接口交付后同用户客户端可使用；应明确这等同于赋予该用户上下文下的命令执行能力，不能视作低风险展示操作。
4. 不将路径、终端 ID、命令参数未经转义直接拼接进 Shell；`FOOFOIL_TERMINAL_ID` 只用于定位上下文，不是授权凭证。
5. 首版不提供向**现有**交互终端任意注入输入的接口；未来若实现，另行设计授权及冲突处理。
6. SSH 使用系统 OpenSSH、`~/.ssh/config` 和 SSH Agent，不自建密码库或保存明文密码。
7. 主应用不启用 App Sandbox；签名、公证与 CLI 安装须在正式交付物上验证，macOS 隐私限制仍然有效。

### 7.1 前置可行性验证（原沙盒路线，结果已记录）

原沙盒路线曾要求以下验证；结果见 §12。主应用取消沙盒后仍需在正式签名交付物上验证对应的传输、文件访问与工具兼容性，不再以原沙盒拒绝作为当前产品阻塞：

1. 外部原生 CLI 到 Unix Socket 的可达性、同用户隔离、宿主冷启动、隐藏状态及多副本定位；不能用 Debug 特有权限代替。
2. `open` 所需文件访问能力如何交付及持久化，覆盖首次访问、应用重启、同路径替换和授权失效。路径字符串和同用户身份不等于 Sandbox 文件授权；可保留现有文件事件作为能力交付适配层，但需验证关联请求和超时。
3. PTY/Shell 能否访问用户选择的工作目录、工具链、SSH 配置及 Agent socket，并记录原沙盒的子进程限制；使用真实 zsh/bash、SSH 和 TUI 验证。

开发签名原型与 Developer ID、公证后的分发验收分别记录，不互相替代。若任一核心目标受阻，应记录限制并修订传输或交付路线，再开始正式集成。

### 7.2 协议确定性

沿用现有协议的确定响应和资源有界原则，在 Socket 适配前固化以下契约：

- 明确长度前缀或其他消息分帧方式、UTF-8 编码、消息大小、连接/读写超时、并发连接及队列上限；完整校验后才能提交操作。
- 保留 request_id、run_id、去重期限及相同 ID 不同参数冲突规则；超时不代表操作未提交。重试须使用相同 ID 和参数，禁止自动重复创建终端。
- 定义操作接受顺序、关闭/隐藏与创建的竞态、成功响应时点及背压；终端创建 ready 表示会话建立，不代表初始化命令或 TUI 完成。
- 明确端点发现、多应用副本选择、过期 Socket 清理和应用重启行为；只清理经验证属于本应用的端点，禁止误删其他实例端点。
- 现有传输和 Socket 适配进入同一控制服务及去重/暂停/撤销路径，避免双入口重复执行。

## 8. 持久化与扩展边界

- 终端启动配置和历史记录应复用现有 SQLite 历史仓库；窗口恢复状态复用既有配置机制，不新增同领域存储层。
- 终端箔在数据层作为一种内容类型，其运行时对象不参与历史序列化。
- 终端箔已确定 **Core 内置**，不通过现有 `extension-kit` 装载；仍遵循通用箔片内容类型、历史和窗口管理约定。
- 不要将 Hi-Fi 等专属能力混入通用控制服务；控制接口应围绕箔片的通用能力与类型协商展开。

## 9. 分阶段实施

### P0a：前置原型与契约

- 完成 §7.1 三项可行性验证，记录签名、权限、复现步骤、成功与限制。
- 固化现有 CLI 与通用控制的命令、作用域、ID、协议升级和迁移契约。
- 固化主动重开/自动恢复、CLI 强制关闭及受管理进程边界。

**验收**：有可复现证据支持 Unix Socket、文件授权和交互式 Shell 路线；阻塞项先解决或调整设计，不带入正式集成。

### P0b：控制能力基础

- 梳理现有 `AppState`、窗口控制器、历史仓库，提取少量可复用应用服务。

## 13. 结论

将「终端箔」定义为**可持久化启动配置的交互式悬浮终端**，将 `foil` 定义为**独立于终端箔的应用控制客户端**。在用户确认的非沙盒站外发行前提下，从已有 Agent 控制实现提取小范围、可测试的统一控制服务并接入交互式终端；不以终端为中心重构整个应用，也不在首版实现会话恢复或任意远程执行。这样既能支持 foofoil 作为 Agent 桌面呈现终端的长期方向，也能维持现有轻量化和扩展边界。
